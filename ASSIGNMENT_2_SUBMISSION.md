# Ассайнмент 2: архитектура, спецификация агентов и прототип

## Тема

**Intelligent Platform for Managing Diploma and Master's Projects with Functions for Assessing Topic Novelty, Eliminating Duplication, Assigning Supervisors, and Monitoring the Basic Completion Cycle.**

## Обоснование многоагентного подхода

Задача не сводится к одному типу рассуждения. Система должна одновременно:

- структурировать тему и входные данные студента;
- сравнить тему с архивом работ и оценить новизну;
- выявить прямое или смысловое дублирование;
- подобрать научного руководителя с учётом компетенций и нагрузки;
- построить базовый цикл выполнения проекта;
- проверить итоговое решение по правилам сдачи.

Эти подзадачи имеют разные критерии завершения, разные источники данных и разные риски ошибки, поэтому они разделены между специализированными агентами. Оркестратор только распределяет задачи и сохраняет состояние.

## Архитектура

Выбрана схема **оркестратор + конвейер + явное общее состояние**.

Подробная схема находится в `docs/architecture.md`.

Агенты:

1. Topic Intake Agent.
2. Novelty Assessment Agent.
3. Duplication Control Agent.
4. Supervisor Matching Agent.
5. Completion Cycle Monitor Agent.
6. Quality Gate Agent.

Оркестратор не выполняет предметную работу, а только передаёт структурированные JSON-сообщения, сохраняет состояние и пишет логи.

## Спецификация агентов

Полная таблица с ролями, входами, выходами, инструментами и критериями завершения находится в `docs/agents_specification.md`.

Кратко:

| Агент | Основная ответственность |
| --- | --- |
| Topic Intake Agent | Проверка и структурирование темы |
| Novelty Assessment Agent | Оценка новизны по архиву тем |
| Duplication Control Agent | Решение о риске дублирования |
| Supervisor Matching Agent | Подбор руководителей |
| Completion Cycle Monitor Agent | Построение базового цикла выполнения |
| Quality Gate Agent | Финальная проверка готовности |

## Форматы сообщений

Агенты обмениваются объектами `AgentMessage` в JSON-формате. Описание форматов находится в `docs/message_formats.md`.

## Внешние инструменты и источники данных

В исходном прототипе использовались:

- `data/archive_topics.json` - архив тем для оценки новизны и дублирования;
- `data/supervisors.json` - база руководителей;
- `data/completion_template.json` - шаблон контрольных точек;
- `runtime/state.db` - SQLite-хранилище состояния, сообщений и вызовов;
- `runtime/agent_calls.jsonl` - журнал вызовов агентов.

## Прототип

Прототип запускает полный сценарий из 6 агентов. Минимальное требование Ассайнмента 2 о взаимодействии минимум 2 агентов выполнено с запасом.

Команда запуска:

```bash
python3 -m src.main --demo
```

Сейчас эта команда использует OpenAlex CSV по умолчанию. Для воспроизведения исторического результата Ассайнмента 2 добавьте `--archive-source sample`.

Команда тестирования:

```bash
python3 -m unittest discover -s tests
```

## Результат демонстрационного прогона

Демо-прогон показал:

- финальное решение: `APPROVE_FOR_TEACHER_REVIEW`;
- все 6 агентов выполнили свои роли;
- распределение вызовов агентов: по 16.7% на каждого агента.

Эта историческая цифра не измеряла реальные вызовы инструментов. Текущий лог Ассайнмента 4 показывает их отдельно: максимальная доля агента в типовом запуске составляет 20%.

Пример JSON-результата сохранён в `artifacts/sample_run_output.json`.
